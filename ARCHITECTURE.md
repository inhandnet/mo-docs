# Content architecture

The repository supplies versioned documentation to the single developer website.
It does not own a Docusaurus project, React implementation, search index or deploy
account. See the bilingual README for repository ownership and governance.

## Content layout and routes

`docs/` retains software chapters and category metadata. `_partials/` contains
shared body text. `hardware/products/` and `hardware/accessories/` hold the
hardware originals. `content/hardware-map.json` maps those originals into the
same `/docs/` navigation. The website is pre-release, so no legacy
`/hardware-docs/` routes or redirect stubs are kept.

`hardware/training/` and `hardware/templates/` remain author resources and are
excluded from product navigation.

`static/` contains media and downloadable resources. Hardware assets are
maintained once under `hardware/` and listed in `content/hardware-map.json`;
developer publishes them under `/docs/` without another hand-maintained copy.
Source and license notices move with the content.

## Content contract

Markdown is the default. MDX may invoke developer's registered components or
import shared content and media. The contract distinguishes actual MDX expressions
from fenced teaching code. It rejects internal frontend imports, arbitrary page
logic, network requests, Hooks, event handlers, inline styles and JSX spreads.

`validation/` is generated by developer's `scripts/export-contract.mjs` from a
specific commit. `contract-lock.json` records the rule version and every rule
file's SHA256. Do not edit those generated files. Update the authoritative rules
in developer, test them, commit them, and export the accepted bundle here.

The child CI uses the pinned bundle; the website rechecks the combination against
its own actual rules. The rule bundle is a validation dependency, not a runtime
website framework. `npm test` also checks resource scripts, model evidence,
mechanical files and repository policy.

## Preview and publication

`npm run preview` calls a sibling developer checkout with this repository as a
local source override. `DEVELOPER_DIR` can select another checkout. The developer
command records source identity, dirty state and file hashes and refreshes edits.
Local overrides are previews and cannot be used in a tagged website release.

Content Release tags use only `VX.Y.Z`. The parser retains historical RC support
for reading old history, but the publication gate rejects new RCs. A release must
use an annotated tag on accepted master ancestry and a clean checkout. The
archive contains content, metadata, licenses, the pinned validation rules and a
file manifest. It contains no website output or environment-specific build.

Developer subsequently freezes a complete release composition and uses the exact
content source/artifacts. Only developer owns RC acceptance, final promotion,
complete-site deployment and rollback. A successful content release is not an
announcement that the website or a board configuration was deployed or tested.

The source-only CI check is `validate-content`, alongside `commit-message`.
Branch protection must require these actual checks when this migration merges.
Historical published Pages/site artifacts remain available until the unified
website migration is accepted; removing a workflow does not constitute that
acceptance or authorize deleting old releases.
