## Request and verify a compliance package

Request the package for the exact model and destination from your InHand contact. A useful review record includes:

| Field | What to verify |
|---|---|
| Product scope | Mo62A model, memory option and PCB/assembly revision match the supplied hardware |
| Issuing party | Manufacturer, responsible party or issuing laboratory is identified as appropriate |
| Document identity | Document/report number, revision, date and complete page count |
| Declaration content | Applicable requirements, referenced standards and authorized signatory, where required |
| Test configuration | Power supply, radio/antenna, cables, enclosure, peripherals and firmware |
| Conditions and exclusions | Restrictions, approved variants and any changes requiring further review |
| Traceability | Original file source, received date and checksum of the retained copy |

Do not generate a signature, stamp, report number or certificate image to fill this gap. If a document is confidential, keep it in the agreed private channel rather than adding it to a public issue or repository.

## Functional tests are different evidence

The [camera capture](../application-development/camera-and-video.mdx), [GPIO/UART/PWM loopbacks](../application-development/gpio-and-peripherals.mdx) and [inference benchmarks](../application-development/ai/benchmarks.mdx) show the behaviour of a development board in specified tests. They do not establish EMC, radio, electrical safety or environmental conformity.

Before production release, have the appropriate compliance reviewer confirm the document scope against the actual integrated product. See [Certifications](./certifications.mdx) for the current evidence status and [Integration notes](./integration-notes.mdx) for configuration information to collect.
