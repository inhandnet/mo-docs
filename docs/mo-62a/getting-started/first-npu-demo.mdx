Run live object detection with the pre-installed `edgeai-demo` launcher. An IMX219 camera supplies the video, a compiled YOLOX model detects common objects, and HDMI shows the annotated image and performance graphs. You do not need to train a model or install an AI development environment for this demo.

You can also [run the supplied sample videos](#run-the-sample-video-no-camera-required) without a camera. Both paths run inference **on Mo62A**. The result screenshots and recording on this page use the video-file path; the camera connection and menu instructions are shown separately.

Mo62A's AI accelerator is the **C7x DSP with its Matrix Multiply Accelerator (MMA)**. TIDL runs supported model operations on this hardware. Python and C/C++ are two application backends; choosing Python does not mean inference runs only on the CPU.

This page covers connecting the camera and running the first AI demonstration. For Bayer/NV12 formats, media topology, ISP tuning files and camera-to-JPEG development without inference, use [Camera & video](../application-development/camera-and-video.mdx). For the software stack and model development, continue to [AI development](../application-development/ai/index.mdx).

| Your starting point | Follow this path |
|---|---|
| IMX219 connected, ready to show a live scene | Start with [camera connection](#1-connect-the-imx219-camera), then initialize and choose the model. |
| No camera, or a repeatable demonstration | Go directly to [sample-video setup](#run-the-sample-video-no-camera-required). |
| Want to inspect the results first | Open the [scene recordings](#actual-video-file-demonstration), then compare C/C++ and Python below them. |

## Before you start

Complete [First boot](./first-boot.mdx), then have the following ready:

- A Mo62A installation that includes `edgeai-demo`, the compatible TIDL runtime and `/opt/model_zoo/`. This walkthrough used a V1.1.0 development installation; a version label alone does not establish the same software or video-decoder fixes.
- For live capture: a supported IMX219 CSI camera and a ribbon cable compatible with both connectors. These are not needed for the sample-video path.
- An HDMI monitor connected to the board and powered on. The launcher uses a 1920 × 1080 output canvas.
- An SSH or debug UART session to control the demo independently of HDMI.
- For live capture: a well-lit scene containing recognizable objects, such as a cup, bottle, keyboard or mouse. Remove any lens cover and keep the lens clear.

The current test board reports TI ONNX Runtime 1.23.0, GStreamer 1.26.2 and TI GStreamer plugins 0.7.0. See the [measured AI stack version map](../resource-download/version-map.mdx) for firmware/library hashes and the distinction between this development installation and a pristine release image. Do not install the x86 compiler environment on the board to run this demo.

:::note[Save your desktop work]
The demo uses HDMI directly and stops LightDM to release the display. This ends the current graphical desktop session. Save open work before starting, and run the commands below from SSH or debug UART. When the demo finishes, LightDM restarts and you may need to log into the desktop again.
:::

## 1. Connect the IMX219 camera

If the board is running, shut it down with `sudo poweroff`, wait for shutdown to finish and disconnect USB-C power. Do not connect or remove the CSI ribbon while the board is powered.

1. Find the **CSI** connector beside the audio jack and Ethernet port. Gently lift its locking bar; do not pull the connector body off the board.
2. Insert the ribbon squarely into the connector, with the exposed contacts facing the board, as required by the connector shown here. Check the orientation at each end of your particular cable; its backing color alone does not identify the contact side.
3. Close the locking bar evenly. The ribbon should remain straight at the socket and should not pull free. Check the camera-end connector too.
4. Position the camera so its lens faces your test objects. Route the ribbon without a sharp crease or strain, then reconnect HDMI and power.

The animation isolates the camera connection and omits other cables. The ribbon is straightened for visibility; allow clearance above nearby connectors when routing the actual cable.

## 2. Initialize and check the camera

After the board boots, log in through SSH or debug UART and run:

```bash
sudo init-imx219
```

This configures the IMX219 media pipeline, creates stable camera device links and writes the active camera configuration used by the launcher. Run it after boot before your first CSI demo; connecting the cable alone does not perform this initialization.

<a href={cameraInit} target="_blank" rel="noopener noreferrer">
  <img src={cameraInit} alt="Actual IMX219 initialization detecting the sensor, configuring 1920 by 1080 RGGB capture and creating stable device links" width="1439" height="899" />
</a>

Check what the launcher will use:

```bash
edgeai-demo status
```

For this camera, look for `CAMERA_ID=imx219`, `VIDEO=/dev/video-imx219-cam0` and `SUBDEV=/dev/v4l-imx219-subdev0`. The numbered nodes behind those links may differ between images. The status command reports configuration and discovered devices; the live image in step 4 confirms that useful camera frames reach the display.

The camera display name can vary between image revisions. Check `CAMERA_ID=imx219`, the device aliases and capture format rather than relying on the descriptive name alone.

## 3. Choose a camera, model and backend

Start the interactive launcher:

```bash
edgeai-demo
```

**Choose the camera.** Enter `1` for **CSI (IMX219)**, or press Enter to accept that default. If it says the CSI camera is not initialized, cancel with Ctrl+C and complete step 2.

<a href={cameraMenu} target="_blank" rel="noopener noreferrer">
  <img src={cameraMenu} alt="edgeai-demo camera menu offering CSI IMX219 and USB, with CSI as the default" width="1439" height="899" />
</a>

**Choose the model.** For a first demonstration, select `ONR-OD-8220-yolox-s-lite-mmdet-coco-640x640`, the COCO general-object detector used in this walkthrough. Choose the `coco` variant, not the similarly named `widerface` model. It is number `3` in the image shown below. Check the displayed name before entering a number: indexes can change when the installed model set changes. Pressing Enter without a model selection cancels the launcher.

<a href={modelMenu} target="_blank" rel="noopener noreferrer">
  <img src={modelMenu} alt="Actual installed models grouped by detection, segmentation, classification and pose, with YOLOX-S-Lite (8220) at index 3" width="1439" height="899" />
</a>

**Choose the backend.** Enter `2` for **C/C++** to follow the main demonstration, or enter `1` / press Enter for **Python**. Both use the model's TIDL artifacts for acceleration. The application pipeline and post-processing implementation differ, so their overall frame rates need not be identical.

<a href={backendMenu} target="_blank" rel="noopener noreferrer">
  <img src={backendMenu} alt="edgeai-demo backend selection after choosing YOLOX-S-Lite (8220), offering Python and C/C++" width="1439" height="899" />

Authenticate if `sudo` requests your board login password. The launcher prints the selected camera, model and backend, stops the desktop, resets C7x and reinitializes the CSI camera before starting inference. Allow a few seconds for this transition; do not start a second demo at the same time.

### Run the same selection directly

After initialization, this command selects the same model without the menu:

```bash
edgeai-demo run ONR-OD-8220-yolox-s-lite-mmdet-coco-640x640 \
  --camera csi --backend cpp
```

Replace `cpp` with `python` to use the Python backend. Use the full model name in repeatable instructions instead of relying on a model index.

To inspect the installed choices without starting inference:

```bash
edgeai-demo list
```

## Run the sample video (no camera required)

Use this path if a camera is unavailable or you want a repeatable scene. Skip steps 1–3: neither a CSI connection nor `init-imx219` is needed. Keep HDMI connected and control the board through SSH or UART.

The current `edgeai-demo` menu accepts CSI and USB cameras. For a file input, the helper below launches the **same installed EdgeAI Python or C/C++ application** with a video configuration. It uses **hardware H.264 decoding** (`v4l2h264dec`) and **TIDL acceleration** for YOLOX-S-Lite (8220). Decoding runs on the VPU; inference runs on C7x/MMA. The file configuration sets `drop: False`, so a faster decoder waits for the inference pipeline instead of decoding and discarding unnecessary frames.

:::note[Video-demo image requirements]
The hardware-decoded example was verified on a test device with the AM62A VPU polling and GStreamer V4L2 format fixes from the Mo62A source tree. These changes have not yet been validated in a newly released image. An older image can contain the demo and models but still lack these fixes; use a build containing them for this video path. The CSI instructions above do not require H.264 decoding.
:::

**1. On Mo62A**, create a working directory:

```bash
mkdir -p /tmp/mo-npu-video
```

**2. On your computer**, download these three files into one directory:

- <a href={useBaseUrl('/downloads/npu-demo/traffic-sample.mp4')} download>traffic-sample.mp4</a> — a 20-second, 1280 × 720 H.264 road video (about 11 MB).
- <a href={useBaseUrl('/downloads/npu-demo/video-demo.yaml')} download>video-demo.yaml</a> — YOLOX-S-Lite (8220), a detection threshold of 0.4, looping video input and HDMI output.
- <a href={useBaseUrl('/downloads/npu-demo/run-video-demo.sh')} download>run-video-demo.sh</a> — checks the input, stops the desktop, runs inference and restores the desktop service when stopped.

From that download directory, copy the files to the board. Replace the username and address with your own:

```bash
scp traffic-sample.mp4 video-demo.yaml run-video-demo.sh \
  YOUR_USERNAME@BOARD_IP_ADDRESS:/tmp/mo-npu-video/
```

**3. In the board's SSH or UART session**, start the C/C++ backend:

```bash
sudo bash /tmp/mo-npu-video/run-video-demo.sh cpp
```

The road scene repeats on the board's HDMI monitor. Look for vehicle boxes and labels as cars enter and leave the scene. Press **Ctrl+C in this same terminal** and wait for the completion message before trying Python:

```bash
sudo bash /tmp/mo-npu-video/run-video-demo.sh python
```

Both backends were tested on Mo62A with this video and YOLOX-S-Lite (8220). `/tmp` is temporary storage; copy the files again if they are removed after a reboot. To return to the camera demo, stop this run and follow steps 2–3.

The input is an excerpt of [Queen Victoria Street (Fremantle Traffic Bridge) south](https://commons.wikimedia.org/wiki/File:Queen_Victoria_Street_%28Fremantle_Traffic_Bridge%29_south.ogv) by **Evad37**, released under [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/). The supplied excerpt uses seconds 5–25, converted to H.264 at 30 fps without audio. Detection boxes are produced by the model on the board.

## 4. Watch and understand the results

Look at the monitor attached to **the board's HDMI port**. The SSH terminal controls the process; it does not receive the video stream.

For the YOLOX object-detection example, move a recognizable object into view. The live image should update, with boxes and category labels appearing when the model detects an object. This model recognizes COCO categories, not arbitrary products or every object in a scene. A missing box alone does not indicate an accelerator failure: check lighting, distance, framing and the model's supported classes.

### C/C++ and Python: same model, same video

Both backends invoke TIDL on C7x/MMA. C/C++ can reduce application and pipeline overhead, but changing the application language does not increase the accelerator's physical compute capacity. The measured benefit in this example is **higher end-to-end throughput**.

For the same 20-second road video and 8220 model, three runs per backend produced:

| Metric | C/C++ | Python |
|---|---:|---:|
| Completed pipeline frames per second, mean | **21.7 FPS** | **17.9 FPS** |
| FPS range across three runs | 21.67–21.73 | 17.82–17.90 |
| Whole-system CPU busy, mean across four cores | 31.4% | 31.2% |
| Application-side `dl-inference` call time, mean | 41.5 ms | 41.5 ms |

C/C++ processed about **21.5% more frames per second** at a similar CPU load. The inference-call times were almost identical. This is consistent with differences in scheduling, data handling and post-processing around inference; this test does not isolate Python's interpreter as the sole cause. The call timer includes runtime invocation overhead and is not an NPU-only kernel timer.

<details>
<summary>Measurement conditions and how to compare</summary>

- One Mo62A test device with the hardware-decoding fixes described above; identical video bytes and compiled model artifacts for both backends.
- 1280 × 720 input at 30 fps; 640 × 640 model input; threshold 0.4; `drop: False`; 1920 × 1080 HDMI output with the same performance overlay.
- Each run discards 600 completed-frame reports for warm-up, then measures the next 600. There are three runs per backend, in the order C++, Python, Python, C++, C++, Python.
- FPS and CPU use the same remote monotonic measurement interval. CPU busy comes from `/proc/stat`, normalized over all four cores. CPU frequency was 1.4 GHz at measurement boundaries; recorded SoC sensor values ranged approximately 76–85 °C. These are observed conditions, not a guarantee of constant thermal behavior.
- Both installed applications enable their existing `-n -v` frame and inference reports. There is no screen recording or input-file transfer during measurement. SSH report collection adds some overhead; the results are rounded and are not a model-only benchmark.
- To compare your own setup, run the **same configuration** once with `cpp` and once with `python`, stop between runs, allow warm-up and repeat in alternating order. Keep the decoder, model, scene, resolution and threshold unchanged. Compare throughput and CPU load separately from model-call timing.

The <a href={useBaseUrl('/downloads/npu-demo/backend-comparison.json')} download>six-run measurement data</a> contains the input checksum, configuration, individual results, temperatures and timing method. These measurements apply to this board, model and scene; other workloads can give different results.

</details>

### Confirm hardware acceleration

At startup, ONNX models print the number of operations assigned to TIDL. In the tested YOLOX-S-Lite (8220) run, both backends reported:

```text
Final number of subgraphs created are : 1, - Offloaded Nodes - 329, Total Nodes - 329
```

This means all 329 model nodes were assigned to the TIDL execution provider in that run. It does not mean the entire camera-to-display application runs on C7x. Combine the startup report with the updating video and `c7x_1` activity when checking the result. Different models can have different offload counts.

### Why file input and CSI input can have different CPU loads

An IMX219 supplies raw Bayer frames to the CSI receiver; the TI ISP and scaler handle much of the image preparation. An H.264 file first needs decoding. With `avdec_h264`, the CPU performs that decoding; with `v4l2h264dec`, the VPU performs it. Both paths still use the CPU for application work, and this hardware-decoded file path includes a copy into TI-compatible image buffers.

A high `mpu` reading therefore does not by itself mean inference fell back to the CPU. Check the decoder, the TIDL offload report and `c7x_1` activity. For a repeatable file demo, `drop: False` avoids processing excess decoded frames; a live camera can instead drop old frames to keep latency low. Compare the same model and backend, and measure without screen recording or large file transfers. A smaller model can finish quickly and show lower C7x activity even while it is accelerated.

FPS depends on the camera, model, backend, image processing, display and thermal conditions. A single demo screenshot is not a benchmark or a performance guarantee.

## 5. Stop or try another model

Press **Ctrl+C in the SSH or UART terminal that launched the demo**. Wait for cleanup and the shell prompt before starting another run. The launcher resets C7x and restarts LightDM; the HDMI display returns to the login screen or desktop.

Run `edgeai-demo` again to choose another installed model. Each task displays a different result:

| Task | What to expect |
|---|---|
| Object detection | Boxes and labels around supported objects. |
| Classification | Class predictions for the image, rather than object locations. |
| Semantic segmentation | Regions of the image colored by predicted class. |
| Pose estimation | Detected body keypoints or skeletons when a person is in view. |

The camera walkthrough uses YOLOX-S-Lite (8220) with IMX219; the recorded detection results use the supplied video file. Availability and behavior of other models depend on the image and model artifacts; consult [Pre-compiled models](../application-development/ai/model-hub.mdx) and [Known issues](../application-development/ai/known-issues.mdx).

### Use a USB camera instead

A compatible UVC camera can be used in place of IMX219. It does not require `init-imx219`. Attach it, check `edgeai-demo status`, then choose **USB** in the camera menu or use `--camera usb` in the direct command. The launcher selects a capture node and prefers MJPEG, with YUYV as a fallback. Camera format and resolution support vary; the screenshots and instructions above use IMX219.

## Troubleshooting

| Symptom | What to check |
|---|---|
| `edgeai-demo` is not found | Verify that you booted the Mo62A image with the demo and model zoo installed. |
| `No IMX219 found` | Power off before checking both ribbon ends and locking bars. Verify that the image enables the IMX219 device-tree overlay. |
| CSI camera is not initialized | Run `sudo init-imx219`, then `edgeai-demo status` before starting inference. |
| Video is black or too dark | Remove the lens cover and check lighting. Use the tested [JPEG capture](../application-development/camera-and-video.mdx#capture-jpeg-frames) to separate camera issues from model issues before changing inference settings. |
| No image appears in the SSH window | Video is sent to the board's HDMI monitor. Check the cable, monitor input and display connection. |
| The desktop terminal disappears | The demo stops LightDM. Control the demo through SSH or UART instead. |
| Camera or display is busy | Stop the previous preview or demo. Do not run multiple applications using the same camera or HDMI output. |
| Model is missing or fails to load | Check `edgeai-demo list` and use an installed compiled model. Review the terminal error and model compatibility. |
| Video appears but boxes are absent | Check the model task, supported classes, lighting, focus and object size. Try a clearly visible COCO object. |
| Desktop does not return after Ctrl+C | Once the demo has stopped, run `sudo systemctl start lightdm` through SSH or UART. |
