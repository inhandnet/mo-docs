Mo62A uses the AM62A's C7x DSP with a Matrix Multiply Accelerator (MMA), TI's deep-learning accelerator, for TIDL-accelerated neural-network inference. The advertised 2 TOPS is a peak hardware capability, not application throughput. Arm Cortex-A53 cores still run application code and can execute network sections through a compatible CPU runtime. They are not guaranteed to remain idle. See [TI's AM62A peak-performance explanation](https://e2e.ti.com/support/processors-group/processors/f/processors-forum/1338450/am62a7-how-mma-2-tops-peak-performance-is-computed).

:::info[Evidence and version scope]
Local results refer to the Mo62A V1.1.0 development installation with TIDL `11_02_17_00` and TI ONNX Runtime 1.23.0, not a pristine TI EVM image. The `2026-08-19` value reported by `mo-version` is an image build field, not the GitHub release date. The diagrams explain software relationships; they are not traces or proof that every depicted path was tested on Mo62A.
:::

## Three things to know first

1. For TIDL acceleration, compile models on a matching x86 host, then deploy the graph, artifacts and application metadata together. Ordinary C/C++ applications can still be built on the board.
2. Use a compatible host/target combination. SDK, TIDL and runtime version numbers need not be identical; changing one component independently can break the integration.
3. CPU fallback is a runtime capability, not a universal rescue mechanism. An unsupported or custom operator still needs an implementation in the chosen CPU runtime.

## The software stack

<a href={stackOverview} target="_blank" rel="noopener noreferrer">
  <img src={stackOverview} alt="Conceptual AM62A stack separating application code, OSRT CPU fallback, TI offload, native TIDL-RT and VPAC vision processing; not a measured call trace" width="2800" height="2380" />
</a>

| Path | Function | Verification boundary |
|---|---|---|
| ONNX Runtime + TI execution provider | Dispatches supported subgraphs to TIDL; remaining supported operations can use the CPU provider | Supplied YOLOX models and a newly compiled 8210 warehouse application were tested |
| TFLite + TI delegate | Uses a different model/runtime integration | Board Python module is 2.12.1; installation is not proof every TFLite model passes |
| TVM runtime | Another TI-supported deployment path | Board module is 0.18.0; no new Mo62A TVM deployment is claimed |
| Native TIDL-RT | Runs compatible fully offloaded artifacts without an OSRT frontend | No OSRT CPU fallback; the board's `tidlruntime` Python package is not installed |
| TIOVX / vision plugins | Connects supported processing nodes and hardware services | Buffer reuse and CPU work depend on the application |

These distinctions follow the [pinned TI runtime overview](https://github.com/TexasInstruments/edgeai-tidl-tools/blob/11_02_17_00/README.md) and [TIDL-RT guide](https://github.com/TexasInstruments/edgeai-tidl-tools/blob/11_02_17_00/docs/tidlrt.md). The SDK 11.01 guide also describes the older Neo-AI DLR integration; an installed DLR 1.13 module is not evidence of a validated TVM 0.18.0 pipeline.

The VPAC provides vision functions such as ISP and scaling. This does not make an entire GStreamer application zero-copy or CPU-free. TI's [AM62A dataflows](https://software-dl.ti.com/processor-sdk-linux/esd/AM62AX/11_01_07_05/exports/docs/edgeai/edgeai_dataflows.html) distinguish OpTIFlow from Python/C++ applications using `appsink`, OSRT and OpenCV postprocessing.

## Initialization and repeated inference

<a href={inferenceFlow} target="_blank" rel="noopener noreferrer">
  <img src={inferenceFlow} alt="Conceptual distinction between session initialization and repeated inference, with conditional CPU fallback and explicit timing boundaries" />
</a>

Initialization loads the model and artifacts and prepares resources. Repeated calls supply inputs, execute the selected runtime path and return outputs. Initialization and the first call can cost more than warmed-up calls, but there is no universal duration or single point at which every failure occurs. This follows [TI's inference guide](https://github.com/TexasInstruments/edgeai-tidl-tools/blob/11_02_17_00/docs/model_inference.md), not a function-by-function trace.

The [benchmark page](./benchmarks.mdx) measures synchronous `session.run` on two supplied models. It excludes capture, input preparation, display and session creation. It is not a hardware-only C7x timer or end-to-end video FPS.

## Subgraph partitioning

<a href={subgraph} target="_blank" rel="noopener noreferrer">
  <img src={subgraph} alt="Conceptual partitioning between TIDL subgraphs and supported CPU operations; fewer subgraphs alone do not establish correctness or end-to-end speed" width="2880" height="2160" />
</a>

Offload depends on the particular graph, shapes, attributes and precision. Inspect compilation logs and the partition visualization, not just operator names. The [TI compilation guide](https://github.com/TexasInstruments/edgeai-tidl-tools/blob/11_02_17_00/docs/model_compilation.md) describes generated network/I/O binaries and runtime visualization.

The two supplied YOLOX models in our benchmark reported:

```text
Final number of subgraphs created are : 1, - Offloaded Nodes - 329, Total Nodes - 329
```

This confirms those runs' partitioning; it does not mean preprocessing, application postprocessing or data movement uses no CPU. Multiple subgraphs can be valid. Measure their performance alongside CPU sections, tensor transfers and the rest of the application.

The separately compiled [YOLOX-tiny-lite 8210 walkthrough](./compile-your-own-model.mdx) reports 326/326 nodes in one TIDL subgraph and checks raw host/target outputs. Its [warehouse application](./tutorial-yolo.mdx) adds CPU-side region rules and event recording. Different graph counts are not interchangeable performance metrics.

## Compatible versions, not identical version strings

<a href={versionMatrix} target="_blank" rel="noopener noreferrer">
  <img src={versionMatrix} alt="Compatibility review of host tools, artifacts and target components using separate manifests rather than identical version strings" width="2400" height="1680" />
</a>

TI classifies `11_02_17_00` as a backward-compatible patch for AM62A SDK 11.01.07.05, with corresponding target firmware/library updates. That does not mean untouched older firmware accepts every newer artifact. Use the [pinned compatibility table](https://github.com/TexasInstruments/edgeai-tidl-tools/blob/11_02_17_00/docs/sdk_version_compatibility_table.md), the image's integration record and regression tests.

An incompatible change can require recompilation. TI explicitly requires it for the SDK 9.2 → 10.0 case in [this AM62A E2E answer](https://e2e.ti.com/support/processors-group/processors/f/processors-forum/1407278/sk-am62a-lp-model-maker-sdk-9-2-and-10-compatible); that is not a rule that every patch invalidates every older artifact.
