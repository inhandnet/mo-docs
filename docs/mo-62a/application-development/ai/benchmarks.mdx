Measure the part of the application you intend to improve. A model-call latency, a video pipeline's completed-frame rate and an accuracy score answer different questions; none can replace the others.

## Measurement scope

| Metric | Includes | Does not establish |
|---|---|---|
| Inference-call latency | Wall-clock time around synchronous `session.run`, including runtime overhead and supported CPU fallback | Camera or video FPS, preprocessing cost, model accuracy |
| Application throughput | Completed frames from input decoding through application processing | A hardware-only NPU execution time |
| System CPU busy | Activity across all four CPU cores during the measurement interval | Power consumption or attribution to one process |
| Accuracy | Task metrics against labeled validation data | Latency or sustained throughput |

The results below come from one V1.1.0 development installation running Linux 6.12.35 and TI ONNX Runtime 1.23.0 with TIDL 11_02_17_00. They are observations, not guaranteed performance limits. The [version map](../../resource-download/version-map.mdx) records the subsequent read-only stack inventory; it is not a pristine-image manifest, and it does not retroactively add unrecorded package versions to the original timing data.

## Reproduce inference-call timing

Download <AssetLink href="/downloads/ai/benchmark-inference.py" download>benchmark-inference.py</AssetLink> to the board (the maintained copy and the raw result records are in the [mo-models](https://github.com/inhandnet/mo-models/tree/master/products/mo62a/benchmarks) repository). Stop other inference applications first, then run:

```bash
sudo python3 benchmark-inference.py \
  /opt/model_zoo/ONR-OD-8200-yolox-nano-lite-mmdet-coco-416x416 \
  --warmup 5 --runs 100 --output nano.json
```

Repeat with `ONR-OD-8220-yolox-s-lite-mmdet-coco-640x640` and a new output path such as `small.json`. The script refuses to overwrite an existing result.

It creates a TIDL session with graph optimization disabled, allocates correctly shaped all-zero input, warms up, and measures 100 synchronous calls with a monotonic clock. Session creation and input allocation are outside the timed region. It checks that outputs are finite, then saves every sample, the model checksum, runtime version, CPU frequency and thermal readings.

Blank input is deliberately a timing-only test. It is not representative calibration data and does not demonstrate detection accuracy. Inspect the runtime's offload report: these two tests each reported 329/329 nodes in one TIDL subgraph. Merely requesting the provider does not guarantee that an arbitrary network is fully offloaded.

| Model | Input | Mean | Median | p95 |
|---|---|---|---|---|
| YOLOX-nano-lite (8200) | 416 × 416 | 10.900 ms | 10.902 ms | 10.980 ms |
| YOLOX-S-Lite (8220) | 640 × 640 | 40.402 ms | 40.406 ms | 40.530 ms |

CPU frequency was 1.4 GHz at both boundaries; the sampled thermal zones ranged approximately 52–57 °C across these runs. An earlier nano run averaged 10.523 ms; repeated measurements vary, so do not treat the last decimal as a product specification.

## Video application comparison

The [first NPU demo](../../getting-started/first-npu-demo.mdx#cc-and-python-same-model-same-video) separately compared the C/C++ and Python backends using the same road video, 8220 model and configuration. Each run discarded 600 completed frames, then measured 600; three runs per backend were interleaved.

| Backend | Completed-frame rate | System CPU busy | Mean inference-call time |
|---|---|---|---|
| C/C++ | 21.70 fps | 31.42% | 41.46 ms |
| Python | 17.86 fps | 31.25% | 41.51 ms |

These measurements used the development board's hardware-decoding fixes described in that tutorial. They are not a claim about an unmodified image or a general ranking of the two languages. Both backends use TIDL; preprocessing, postprocessing and scheduling differ around the runtime call.

## Newly compiled warehouse application

The [warehouse tutorial](./tutorial-yolo.mdx) uses a newly calibrated YOLOX-tiny-lite 8210 bundle, not either supplied model above. Three consecutive offline runs processed the same 611-frame, 1280 × 720 clip with one TIDL subgraph and 326/326 nodes offloaded. There was no warm-up discard; the first call is included. These are short repeatability checks, not endurance or labeled accuracy tests.

| Run | Elapsed | Processing rate | Mean call | p95 call |
|---|---|---|---|---|
| 1 | 77.620 s | 7.872 fps | 17.616 ms | 17.987 ms |
| 2 | 78.119 s | 7.821 fps | 17.608 ms | 17.998 ms |
| 3 | 77.451 s | 7.889 fps | 17.622 ms | 18.022 ms |

The timer covers input checksum calculation, OpenCV software decoding, preprocessing, inference, zone rules, rendering and MJPEG/file output, excluding session creation. No screen capture or large-file transfer ran during these timed loops. The source/output timeline is 30 fps; it is not the measured processing rate. The 17.6 ms call is not a hardware-only MMA timer.

All three runs produced identical per-frame detections and states, with events at 7.367 s and 8.667 s of source time. The original 8200 baseline passed before and after, with the same boot and remote processor running. Thermal readings at those checks were approximately 54–55 °C, not continuous temperature monitoring. No power data was collected. The model visibly misses small/occluded people; output consistency is not a recall or mAP result.

## Make a fair comparison

Keep the board, image, model bytes, artifacts, input, resolution and threshold fixed. Record warm-up, run length, background applications, cooling, clock policy and the exact timer boundaries. Alternate test order and report individual runs as well as a summary. Avoid recording or transferring screenshots during a timed interval.

Do not convert `1000 / latency_ms` into claimed end-to-end video FPS: it ignores the rest of the pipeline. Do not compare the all-zero timing input with a published accuracy benchmark, and do not infer energy efficiency from CPU utilization.

For accuracy, use labeled data that represents the intended deployment and compare the same preprocessing, class mapping and postprocessing before and after quantization. For power, measure at a stated electrical boundary with a suitable meter and record what peripherals are included.

## TI cross-check

The [AM62A performance guide](https://software-dl.ti.com/processor-sdk-linux/esd/AM62AX/11_01_07_05/exports/docs/edgeai/measure_perf.html) describes SDK performance tools. TI's [AM62A E2E answer](https://e2e.ti.com/support/processors-group/processors/f/processors-forum/1293166/processor-sdk-am62a-measuring-ai-hardware-performance) distinguishes core/resource utilization from AI performance. These references explain measurement boundaries; they are not the source of the Mo62A numbers above.

The downloadable timing script is retained unchanged with its original JSON measurements. The separate [Python smoke test](./inference-apis.mdx) follows the newer wrapper's explicit I/O-validation settings; do not silently treat two different scripts as the same benchmark configuration.
