## What has actually been checked

The tested board exposes OP-TEE device nodes and an initialized kernel driver. This does not establish the board's security lifecycle, enrolled keys, authenticated boot policy or protection of an application secret.

| Item | Observation in this review | What it does not prove |
|---|---|---|
| OP-TEE driver | Kernel log reports revision 4.6 and an initialized driver | Customer-key secure boot is enforced |
| TEE nodes | `/dev/tee0` and `/dev/teepriv0` exist and are root-only | A particular trusted application passes its tests |
| User-space helper | No `tee-supplicant` process was running at the observation time | All OP-TEE services or secure storage are operational |
| Customer keys / OTP | Not inspected or programmed | Production provisioning or recovery has been qualified |
| Secure-boot negative tests | Not performed | An altered or unauthorized image is rejected |

The [OP-TEE client documentation](https://optee.readthedocs.io/en/latest/building/gits/optee_client.html) describes `tee-supplicant` as a normal-world helper for services such as filesystem access. Its absence in this capture is a boundary of the tested environment, not a claim that the kernel driver failed to initialize. No trusted-application, secure-storage or key-isolation test was run.

## Read-only inspection

These commands inspect existing state; they do not enroll keys, replace firmware or invoke a trusted application:

```bash
sudo ls -l /dev/tee*
ls /sys/bus/tee/devices
sudo dmesg | grep -i -E 'optee|op-tee'
pgrep -x tee-supplicant
```

`pgrep` returns a nonzero status when no process matches. Do not change device permissions to `0666` or start an unknown helper merely to make a screenshot look successful. Keep full boot logs private until reviewed for sensitive data.

## Provisioning is a separate, controlled operation

:::danger[Do not experiment with OTP on a working board]
OTP/keywriter operations can make permanent security-state changes and can leave a device unable to boot if the keys, configuration or procedure are wrong. This guide intentionally provides no fuse-programming command. No OTP write, lifecycle transition, key revocation or bootloader replacement was performed for this documentation.
:::

Before any production provisioning, obtain a Mo62A-specific procedure confirmed for the exact SoC/security variant and board revision. It must cover key ownership, protected key storage, authorized signing, backup/recovery, programming supply requirements, verification and failure handling. Use a designated test unit and explicit authorization for irreversible steps.

The SDK includes multiple boot image variants. A filename containing `hs`, `hs-fs` or a signature is not, by itself, proof of the installed device's lifecycle or enrolled customer key. Do not select or replace `tiboot3.bin` from the filename alone.

Development/example keys and keys present in shared source packages must not be treated as confidential production roots. Never put a production private key, device secret or provisioning credential into a repository, screenshot, issue, log archive or Release.

Verify the document, installer, MCU+ SDK, SoC revision and board-specific programming requirements as a set before using any provisioning tool. An AM62Ax evaluation-board procedure is not automatically a validated Mo62A production procedure. TI's [AM62Ax secure-boot reference](https://software-dl.ti.com/mcu-plus-sdk/esd/AM62AX/latest/exports/docs/api_guide_am62ax/SECURE_BOOT.html) explains the platform concepts; use version-matched guidance for implementation.

## Acceptance still required

A production security review must define and verify the intended boot chain, authorized-image acceptance, altered-image rejection, update/rollback policy, key custody and recovery path. Those outcomes remain unverified here. See [Users & security](../mo-os/users-and-security.mdx) for normal Linux hardening and [Security](../../security/index.mdx) for shared security guidance.
